# 05 · 业务逻辑详解

## 一、用户注册与登录

### 1.1 注册流程

```
POST api/v1/register/reg
│
├─ 参数校验
│   ├─ account: 6-16位 字母数字，不含中文
│   ├─ password: 必填
│   ├─ invite: 邀请码（必填）
│   └─ code: 验证码（可选，视注册配置）
│
├─ Register::reg()
│   ├─ 检查注册开关（isRegisterOff）
│   ├─ 检查黑名单（账号/手机/邮箱黑名单表）
│   ├─ 检查重复（users 表 name 字段）
│   ├─ 验证邀请码
│   ├─ 调用 Synapse Register API 创建 Matrix 账号
│   │   → POST /_matrix/client/r0/register
│   │   → 获得 user_id、access_token、device_id
│   ├─ 插入 ext_users 扩展记录
│   └─ 返回 access_token、user_id 等
│
└─ 响应：{access_token, user_id, device_id, home_server}
```

### 1.2 登录流程

```
POST api/v1/login/login
│
├─ 参数：identifier（账号/靓号/手机/邮箱）+ password
│   兼容旧版：phone/email → identifier 映射
│
├─ Index::login()
│   ├─ 判断 identifier 类型（手机/邮箱/靓号/普通账号）
│   ├─ 如是靓号：从 ext_pretty_numbers 查找对应 user_id
│   ├─ 拼装 Matrix MXID：@username:{default_home_server}
│   ├─ 调用 Synapse Login API：
│   │   POST /_matrix/client/r0/login
│   │   body: {type:"m.login.password", identifier, password, device_id}
│   └─ 返回 Synapse 响应（access_token, device_id 等）
│
└─ home_server 始终以服务端 domains.default_home_server 为准
```

### 1.3 验证码发送（限流）

验证码发送受三级时间窗限流（表 `ext_verify_codes`）：

| 时间窗 | 最大次数 |
|--------|----------|
| 1 分钟 | 1次 |
| 1 小时 | 5次 |
| 24 小时 | 10次 |

支持 **手机验证码**（`SmsService`）和 **邮箱验证码**（`PHPMailer`）。  
`verify_type` 区分用途：`register` / `bind_account` / `rebind_verify_old` / `rebind_bind_new`

## 二、用户资料同步机制

当用户修改**昵称**或**头像**时，`ProfileSyncService` 会将新值同步写入所有冗余存储昵称/头像的业务表：

```
UsersDao::setNickname() / setAvatar()
  └─ 更新 ext_users 表
  └─ 调用 Synapse PUT /profile/{user_id}/displayname (或 avatar_url)
  └─ ProfileSyncService::syncNickname() / syncAvatar()
       ├─ ext_circle_users（圈子成员）
       ├─ ext_group_users（IM 群组成员）
       ├─ ext_circle_content（帮办内容发帖人）
       ├─ ext_circle_notice（圈子公告）
       ├─ ext_circle_invite（邀请记录，双向）
       ├─ circle_content_report（投诉记录）
       └─ ext_user_notes（笔记）
```

> ⚠️ 此同步在同一事务内执行，调用方需已开启事务。

## 三、账变推送（WebSocket）

```
业务操作（积分变动/诚信保变动）
  └─ AccountChangeNotifyService::notify(ext_user_id, payload)
       └─ Redis PUBLISH account_change {"user_id":..., "ts":..., ...}

Redis 订阅进程（常驻 Process）
  └─ 收到消息 → 查找 user_ws:{ext_user_id} SET
       └─ 遍历 worker_id:fd → 向对应 fd 推送 WS 消息
```

前端收到消息后应**主动调用** `GET api/v1/users/account` 刷新积分/余额，不依赖 Push 消息中的金额字段。

## 四、圈子（Circle）业务

### 4.1 圈子类型
- `public`：公开圈子，搜索可见，申请需满足邀请人数条件
- `private`：私密圈子，仅邀请可进

### 4.2 成员角色
- `owner`：圈主，全部权限
- `admin`：管理员，可管理成员和内容
- `member`：普通成员，权限受 `can_view_help` / `can_post_help` 控制

### 4.3 入圈流程
```
公开圈子申请：
  用户邀请 N 位好友（ext_circle_invite） → 邀请数满 invitation_code_count → 提交申请（ext_circle_invite type=1）→ 管理审核

管理直接邀请（直接入圈）：
  管理员调用 circle_invite → 直接插入 ext_circle_users（join_method=direct）
```

### 4.4 积分分数显示（user_score）
`ext_circle_users.user_score` = `ext_user_accounts.credit_amount`（诚信保余额）  
当诚信保余额变动时，`ProfileSyncService::syncUserScore()` 同步更新。

### 4.5 帮办内容（ext_circle_content）
- 发帖需权限：`can_post_help = true` 或为 `owner`
- 圈子 `ban_status=1` 时仅 `owner` 可发
- 支持等级限制（`limit_level_status`）
- 支持城市过滤显示

## 五、笔记（Notes）业务

### 5.1 笔记类型
| type 值 | 说明 |
|---------|------|
| 0 | 普通笔记（受 `max_notes_created` 限制） |
| 1 | 超级笔记（受 `max_notes_created` 与墙限制） |

### 5.2 权限控制
- `ext_users.note_creation_prohibited = true`：禁止新建笔记（仍可编辑）
- 每日查看上限：通过 `ext_user_notes_log` 统计
- 笔记墙访问：通过 `ext_user_permissions`（`note_access=true`）控制谁能看我的笔记

### 5.3 会员等级对笔记的影响
通过 `ext_user_levels` 配置：
- `max_notes_created`：最大创建笔记数
- `max_notes_per_wall`：每墙最大笔记数
- `max_super_note_wall`：超级笔记墙数量上限

## 六、VIP 会员兑换

```
POST api/v1/vip/exchangeMemberLevel
  └─ 验证 level_id（10001/10002/10003）且 is_exchangeable=true
  └─ 若当前已是目标等级 → 直接返回成功（不扣分）
  └─ 从 ext_user_accounts 扣除 exchange_cost 积分
  └─ 写账变记录
  └─ 更新 ext_users.member_level_id + member_expired_at
  └─ AccountChangeNotifyService.notify() → WS 推送
```

## 七、手机/邮箱绑定与换绑

### 7.1 首次绑定（单步）
1. 发送验证码（`verify_type=bind_account`）→ 落库 `ext_verify_codes`
2. `POST users/bind-phone`：校验验证码 → 更新 `ext_users.phone`

### 7.2 换绑（两步）
| 步骤 | verify_type | 接口 |
|------|-------------|------|
| 第一步：验证旧号/邮箱 | `rebind_verify_old` | `rebind-phone/verify-old` |
| 第二步：绑定新号/邮箱 | `rebind_bind_new` | `rebind-phone/bind-new` |

第一步成功后返回 `rebind_token`，第二步需携带此 token 防止 CSRF。

## 九、后台管理（Backend）典型操作链

以「封禁用户」为例：

```
web-ht 点击封禁
  → POST /ht/v1/userExts/setPenalty
  → UserExtsController::setPenalty
  → UserExtDao::setPenalty
      ├─ 更新 ext_users.chat_prohibited / is_banned 等
      ├─ 调用 Synapse Admin API：
      │   PATCH /_synapse/admin/v2/users/{user_id}
      │   body: {deactivated: true} / shadow_ban 等
      └─ 写 admin_logs 操作日志
```

关键原则：**先改 ext_users 业务字段，再调 Synapse Admin API，记录操作日志。**
